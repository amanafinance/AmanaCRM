# Защита CRM и ежедневные копии — 17.11.2026

Изменения подготовлены в коде. Этот файл не подтверждает обновление рабочего
сервера, доставку настоящего письма или удаление удалённой базы.

## Что изменено

| Проблема | Исправление |
| --- | --- |
| Достаточно украденного пароля | Новый вход требует также код из письма; код действует 5 минут |
| После выхода остаются данные клиентов | Удаляются локальные базы браузера, выход распространяется на другие вкладки |
| Выбор защиты файла | По желанию владельца: обычная копия без пароля или шифрование AES-256-GCM с паролем |
| Нет ежедневной отправки | В настройках владельца: почта, время по Москве, защита паролем по желанию, включение; статус и отправка сейчас |
| Два устройства могут вывести один остаток вклада | Сервер пересчитывает доступный капитал и прибыль в момент записи, в одной транзакции с кассой |
| Проверки можно обойти прямым запросом | Проверки суммы, кассы, графика, закупки, связанных платежей и закрытых месяцев выполняет сервер |
| Действие может остаться без истории | Историю создаёт сервер, она сохраняется вместе с изменением; клиент не может её подделать |
| Архив скрывает долг | Новый архив с долгом запрещён; старые архивные долги учитываются в контроле и портфеле |
| CRM ещё обращается к прежней облачной базе | Старый адаптер, библиотеки, правила и тестовое окружение удалены из проекта |

Выгрузка Excel — отдельный отчёт с доступными пользователю данными, без пароля;
это не полная резервная копия. Уже скачанные файлы выход из CRM не удаляет.
Пароли от сервера и почты не добавлены в репозиторий. Тестовые пароли относятся
только к вымышленным пользователям временной базы.

## Перед установкой на рабочий сервер

Эти шаги выполняет администратор сервера. Ветка `main` автоматически попадает
на рабочий сайт примерно через 5 минут, поэтому сначала выполните подготовку.

1. Остановите таймер автообновления на время работ: `systemctl stop amana-update.timer`.
2. Сохраните текущую базу и файлы сервера в закрытом месте. Проверьте, что копия
   открывается на отдельном тестовом сервере; не загружайте личные данные в GitHub.
3. Установите PocketBase **0.40.6**, Python 3 и `python3-cryptography`.
   Обновлённый `server/setup.sh` рассчитан на эту версию; существующему серверу
   одних новых файлов сайта недостаточно для установки зависимостей.
4. **До миграции** подключите SMTP в панели PocketBase (`/_/` → Settings → Mail),
   укажите отправителя и проверьте доставку тестового письма на почту владельца.
   Убедитесь, что почта в учётной записи владельца действующая и доступна ему.
   Новая миграция потребует код при входе и сбросит прежние входы. Без рабочей
   доставки писем сотрудник войти не сможет. Административный вход PocketBase
   не меняется этой миграцией и нужен для исправления настройки почты.
5. Проверьте, что в службе **нет `AMANA_TEST=1`**. Эта переменная только для
   отдельной временной базы тестов; она открывает вспомогательные тестовые маршруты.
6. Установите сайт вместе с `vendor/amana-model/`, всеми `pb_hooks` и
   `pb_migrations`. Новая миграция — `1794870000_amana_security.js`.
   Сервер должен читать общий расчёт по пути
   `/opt/pocketbase/pb_public/vendor/amana-model/model.js`.
   После подготовки перезапустите PocketBase и проверьте журнал запуска.
7. Войдите как владелец с паролем и настоящим кодом из письма. В «Справочниках»
   выберите почту, время и нужна ли защита файла паролем. При включённой защите
   задайте отдельный пароль копий. Сохраните настройки,
   нажмите «Отправить сейчас», откройте вложение через восстановление на
   тестовом сервере и проверьте состав. На рабочей базе восстановление не запускайте.
8. Проверьте следующую автоматическую отправку и статус в настройках. Затем
   возобновите таймер: `systemctl start amana-update.timer`.

Почтовые настройки видит только владелец. Они хранятся в закрытой коллекции
`amanaBackup`. Если включена защита, пароль хранится в зашифрованном виде;
при отключении защиты он удаляется. Для защищённых копий ключ создаётся в
`/opt/pocketbase/.amana-mail-key` с правами `600` и не попадает в выгрузки CRM.
Для восстановления самого сервера сохраните этот ключ отдельно и защищённо.
Копия CRM не содержит пользователей, паролей входа и настроек SMTP: после
переезда их настраивают на новом сервере отдельно.

Вложение ограничено примерно 18 МиБ. При превышении будет понятная ошибка;
ручная выгрузка остаётся доступной. Сервер повторяет неудачную отправку через
30 минут, не допускает параллельных отправок и обычных повторов за один день.
Если почтовая служба приняла письмо, но не доставила его, статус сервера этого
не доказывает — первый запуск обязательно проверяют по реальному письму.

## Завершение удаления старой базы Firebase

Код CRM больше не использует Firebase. Старые данные в Google этим не удаляются.
Доступ к консоли Google и реальные копии в этой рабочей среде отсутствуют,
поэтому сверка переноса, закрытие удалённого доступа и удаление не выполнены.

Порядок после получения доступа:

1. На время сверки прекратите изменения старой базы. Получите полную копию
   прежних данных и зашифрованную копию текущей CRM, сохраните их в закрытом месте.
2. Сверьте все договоры, клиентов, платежи, кассовые операции, счета, инвесторов,
   операции инвесторов и закрытые месяцы. Сравните число и номера записей,
   суммы денег, остатки счетов и долги. Различия из-за дальнейшей работы в новой
   CRM нужно объяснить по истории, а не просто игнорировать.
3. Проверьте восстановление копии на отдельной базе. Прежние историю и корзину,
   если они не переносились в новую CRM, сохраните отдельно; восстановление
   CRM намеренно не перезаписывает текущую историю и корзину.
4. Закройте чтение и запись старой Firestore правилами `allow read, write: if false`,
   отключите прежние способы входа, отзовите сервисные ключи и проверьте отказ
   доступа извне. Это делает владелец проекта в Google; удаление файла правил
   из GitHub само по себе ничего в Google не меняет.
5. После успешной сверки и восстановления удалите старые Firestore, Auth,
   Storage и ненужные экспорты/резервные копии, если они есть; удалите ненужный
   проект. Проверьте также отдельные хранилища Cloud Storage и доступ сотрудников.
   Зафиксируйте дату и результат удаления без персональных данных.

Для выбора почты и места хранения копий учитывайте персональные данные клиентов.
Шифрование копии само по себе не подтверждает соблюдение требований российского
законодательства или законность ведения бизнеса.

## Проверка изменений

Автотесты используют только временную базу и вымышленные данные. Внешние SMTP
письма не отправляются: коды и зашифрованные вложения перехватываются в памяти.
Оформление возврата товара и денег в это изменение не входит.
Проверяются вход с двумя факторами, ограничения сервера и конкурентные выводы,
касса, архив, атомарная история, оба режима почтовых и ручных копий, расписание с повтором после
ошибки, совместимость копии с восстановлением и очистка браузера при выходе.
Инструкции запуска — [tests/README.md](tests/README.md).
